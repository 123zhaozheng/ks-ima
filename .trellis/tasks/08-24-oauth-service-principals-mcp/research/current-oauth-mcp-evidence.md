**Research date:** 2026-08-26  
**Research agent:** zhaozheng  
**Scope:** post-identity, workspace authorization, knowledge/storage, and search/Ask commits. Planning evidence only.

## Decision Summary

Use interactive OAuth 2.1 authorization-code with PKCE as the default for MCP clients. It preserves the end user's current Python identity, membership, ACL, disablement, and workspace-archive decisions at every request. Use explicit, expiring service-principal credentials only for unattended agents. Both credential classes must invoke the same Python application services (`WorkspaceService`, `KnowledgeService`, `StorageService`, and `SearchService`); neither may retain a parallel Bun authorization/knowledge implementation.

Do not make the legacy `connector` table the OAuth authority. It is a narrow legacy API-key record tied to a creator and legacy `public` workspace/entity schema. Preserve it only as a bounded coexistence input until its MCP route is moved or retired.

### Critical gaps

- No OAuth authorization server, authorization endpoint, token endpoint, refresh token flow, authorization-code/PKCE verifier/challenge store, client registration, consent grant, bearer access-token validation, token introspection, or token revocation endpoint exists in either runtime.

## OAuth 2.1 and MCP Requirements

These are the standards requirements the design must satisfy, subject to final pinning against the current MCP and OAuth drafts/RFCs during implementation:

- Use OAuth 2.1 authorization code with PKCE (`S256`) for interactive native/desktop/browser MCP clients. Require a `code_challenge` at authorization time and verify `code_verifier` once at token exchange. Do not support implicit or resource-owner-password grants.
- Treat the MCP URL as a protected resource. On missing/invalid bearer authentication, return `401` with `WWW-Authenticate: Bearer resource_metadata="https://<public-origin>/.well-known/oauth-protected-resource[/mcp]"` (resource-specific path form when appropriate). Publish protected-resource metadata with the canonical resource URL and `authorization_servers` list.
- Publish OAuth authorization-server metadata at the discovery location required by the issuer/path deployment. Include `issuer`, `authorization_endpoint`, `token_endpoint`, supported `response_types`, `grant_types`, PKCE `S256`, token-auth method expectations, and supported scopes. Discovery URLs and issuer/resource identifiers must be public HTTPS values, not Docker hostnames or Caddy internal routes.
- Validate resource/audience binding. An access token accepted by `/mcp` must have the MCP protected resource as its audience/resource; reject tokens minted for another API. Use opaque access tokens with server-side lookup for the MVP because the existing identity system is server-side and revocation-centric; this avoids introducing signing/JWKS lifecycle before it is needed.
- Dynamic Client Registration is optional for the MVP. If not implemented, support pre-registered confidential clients plus public clients identified by redirect URI/client ID only where native-client security permits. Never use a client secret as proof for a public desktop client.
- Authorization requests must validate client and exact redirect URI, state, PKCE, requested scope/resource, active user session, and current target workspace authorization before issuing an authorization code. Codes must be short-lived, one-time, server-side digested, and bound to client, redirect URI, resource, user, scopes, PKCE challenge, and session/security stamp.
- An OAuth consent page is required when a client first requests a grant or asks for broader access. It must name the client, exact protected resource, requested workspace/folder target, scopes, duration, and whether the request can write. Re-consent only when approved grant does not cover a new client/resource/scope/target combination. No hidden consent from an existing browser session.

## Scopes, Grants, Refresh, Reduction, and Revocation

- Define scopes in terms of target application actions, with no scope that bypasses ACLs. Recommended MVP: `mcp:workspaces:read`, `mcp:knowledge:read`, `mcp:knowledge:search`, `mcp:knowledge:ask`, `mcp:knowledge:write`. Each tool additionally evaluates the current membership and folder ACL action at call time.
- Record an authorization grant with user, client, protected resource, workspace ID, optional folder root, approved scopes, issue/update/expiry/revocation timestamps, and a version/revocation epoch. A narrowed folder root and scope set are an authorization boundary, not UI metadata.
- Scope requests may only be narrowed during consent or token issuance. Refresh must preserve or reduce the original grant; it must never add a scope, workspace, or folder. A token exchange can request a subset only.
- Issue short-lived access tokens (for example 5-15 minutes) and rotating refresh tokens only when a client has received explicit user consent and the operator accepts the theft/reuse risk. Store only peppered token digests; bind refresh records to grant/client/resource; rotate atomically; revoke the token family on replay. No refresh token is necessary for the first narrow MVP if desktop clients can reauthorize, but the schema should not preclude it.
- Immediately deny access tokens and refresh tokens when the grant/client/user/service principal is revoked, the user is disabled, the workspace is archived, membership is disabled/removed, or target ACL denies the requested action. For opaque tokens, database lookup plus current target authorization naturally covers these conditions. Record safe audit outcomes for authorization approval/denial, code exchange, refresh, token revocation, and tool call allow/deny.

## Service Principal Credential Policy

- Add target-owned service-principal and credential records in `ima`, distinct from users and legacy connectors. A service principal has workspace ownership, display name, optional folder root, allowed action/scopes, lifecycle (`active`, `disabled`, `revoked`), audit actor/creator, expiry, network policy, and rate policy. It is never an implicit workspace administrator and does not derive permissions from a human creator after issuance.
- Require an explicit target authorization grant for a service principal: its scopes/folder root must be no broader than a workspace admin explicitly approved. Authorization remains intersection of service-principal grant and current folder ACL policy. If the product must let principals access folders without a human membership row, introduce `subject_type='service_principal'` in target ACLs deliberately; do not fake it as a user or rely on legacy role mapping.
- Credential issuance returns a high-entropy secret once, using a distinguishable prefix/key ID. Store only a peppered digest (prefer an HMAC/pepper construction aligned with `IdentityService._token_digest`, rather than unpeppered SHA-256), a nonsecret prefix, credential ID, created/last-used/revoked/expiry timestamps, and replacement lineage. Never store raw values, log them, put them in audit metadata, or display them after issue/rotation.
- Rotation creates a new credential atomically and explicitly selects either immediate old-credential revocation (default for user-visible rotation) or a short, recorded overlap expiry when needed for an unattended deployment. Revoke/disable immediately invalidates every credential. Enforce mandatory finite expiry for unattended credentials, with a conservative maximum configured server-side; do not retain the legacy empty-expiry default.
- Network policy should default to no CIDR pinning in the first client-compatible release, then support optional validated source CIDR/IP allowlists at the public resource boundary. Never trust forwarded client IP unless Caddy/ASGI trusted-proxy policy supplies it. `Settings.trusted_proxies` and `ProxyHeadersMiddleware` are already present. Evidence: [config.py](D:/code/python/nyaai/backend/src/ima/config.py:23), [app.py](D:/code/python/nyaai/backend/src/ima/api/app.py:160).
- Apply rate and concurrency policy per credential/principal and per source bucket, not only per IP: defaults should separately cap authorization/token endpoints and MCP tool calls; persist the same safe digest/bucket pattern as `ima.auth_rate_limits`; return `429`; audit blocked outcomes without raw credentials or query/content.

## Python MCP SDK and Dependency Choice

- No Python MCP SDK, FastMCP, OAuth library, JWT/JWKS library, or authorization-server dependency is present in the Python lock/project dependencies. Evidence: [pyproject.toml](D:/code/python/nyaai/backend/pyproject.toml:6).
- Bun already pins the official MCP SDK and has a Streamable HTTP server plus official-client handshake coverage. The smallest transition is therefore to retain Bun only as a protocol transport temporarily and make it call a new private, typed Python MCP application adapter after it validates a Python-issued bearer credential. This still requires ownership clarity and adds bridge complexity.
- Recommended MVP ownership is Python/FastAPI for OAuth, credential validation, audit/rate enforcement, target application service calls, and Streamable HTTP MCP transport. Select the official Python MCP SDK only after verifying its pinned release supports ASGI/FastAPI-compatible Streamable HTTP transport and the needed stateless mode. Do not add FastMCP merely for convenience until it is verified compatible with the same transport/version and does not take over OAuth semantics.
- OAuth itself should be implemented with the existing SQLAlchemy/FastAPI patterns plus a narrowly selected, pinned OAuth helper only if it materially reduces protocol-risk. Do not add a broad IdP/OIDC server framework for this local authority. Opaque tokens do not need JWT libraries in the MVP.

## Recommended MVP

1. Add target `ima` migrations for OAuth clients/grants/codes/access tokens/refresh tokens/revocations and service principals/credentials/rate buckets. Use opaque, pepper-digested, indexed token/secret values; do not alter `public.connector` behavior.
2. Implement Python `McpAuthorizationService` and `McpService` that compose existing target application services. Introduce a normalized internal MCP actor (`human grant` or `service principal`) containing client/principal, workspace/folder boundary, allowed scopes, and correlation ID.
3. Implement public OAuth discovery, authorization, token, and revocation routes. Reuse Python session/current/recent-auth mechanics for browser authorization and a dedicated consent UI. Require code+PKCE and `resource`; issue short opaque access tokens. Start without refresh only if the intended supported MCP clients reauthorize correctly; otherwise implement rotating refresh tokens before declaring desktop support complete.
4. Serve Streamable HTTP MCP from Python using a pinned, verified Python MCP SDK. Declare only target-backed read/search/Ask tools first. Add mutating tools only after MCP input includes target optimistic-concurrency/version fields and the service-level error mapping is settled.
5. Add service-principal administration: finite expiry required, restricted scope/folder root, one-time credential display, immediate revoke, default immediate rotation, auditable last use and denial. Keep this path visually and semantically separate from interactive OAuth.
6. Route public MCP/OAuth/discovery explicitly through Caddy to Python; retain `/api/v1/internal/*` blocking. Keep legacy Bun `/api/mcp` only during documented coexistence, then redirect/retire after interoperability and data parity validation.

## Risks Requiring an Explicit Product Decision

- Whether service principals become first-class ACL subjects. Without this, they must be modeled as constrained delegated grants and cannot receive independent folder ACL entries. The latter is acceptable for an initial, workspace-admin-approved automation scope but limits delegation semantics.
- Whether refresh tokens are MVP. OAuth interoperability is stronger with rotating refresh tokens, but initially supporting only short-lived access tokens and reauthorization can reduce secret lifecycle surface if all chosen MCP clients handle it.
- Whether the public resource URL remains `/api/mcp` for compatibility or moves to `/mcp`. Keep one canonical resource identifier; aliases must not produce ambiguous audience/metadata values.
- Whether legacy connector keys are migrated, maintained through a sunset, or immediately revoked after target service credential release. They should not silently become service-principal credentials because their creator-impersonation semantics, unpeppered hash, and optional no-expiry policy differ.
